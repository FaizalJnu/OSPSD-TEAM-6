Level 2: Connect to a Real Provider
Your operation works locally. Now make the same operation using the real provider your team selected.
2.1. Your goal
Replace the fixed or locally defined behavior from Level 1 with a real provider call.
The public behavior of your service should remain the same from the caller's point of view.
For example:
GET /<resource-type>/{id}
should still return the response shape your team defined in Level 1, but the data should now come from the provider.
Your caller should not need to know how the provider represents the underlying object.
2.2 What should happen?
A request should now travel through your service to the real provider and back:
caller
   ↓
your HTTP API
   ↓
application code
   ↓
provider API or SDK
   ↓
real provider





The provider may return data in a shape that looks very different from your public API.
For example, your service may promise:
{
  "id": "resource-123",
  "name": "Example resource"
}
while the provider returns many additional fields or uses different names.
Translate the provider response into the contract your service already exposes.
Do not change your API merely because the provider uses a different representation.
2.3. Specification
The operation from Level 1 must now use the real external provider.
Your implementation must:
authenticate with the provider;
call the appropriate provider operation;
retrieve or perform the behavior represented by your public operation;
translate the provider response into your service's response model;
preserve the public contract defined in Level 1.
Provider-specific credentials and configuration must not be committed to the repository.
Document the configuration necessary to run the service locally.
2.4. What you need to think about
Before implementing, investigate the provider API and agree as a team on:
Which provider operation corresponds to your public operation?
What authentication or credentials does it require?
Which provider fields are necessary to satisfy your public contract?
Which provider fields should remain hidden?
Does the provider use identifiers that your service can expose directly?
Does the provider SDK or API perform any behavior you did not expect?
Which assumptions from Level 1 no longer hold now that real data is involved?
Read the provider's documentation before relying on examples from tutorials, generated code, or coding agents.
If the documentation is ambiguous, record the assumption your team chooses.
2.5. Verify the integration
You should be able to run the service locally with a test account and exercise the operation against the real provider.
Use the simplest available tool for inspecting the request and response, such as curl, your API documentation interface, or another HTTP client.
For example:
curl http://localhost:<port>/<resource-type>/<id>
should return data derived from a real provider resource.
You should also inspect what happens inside the provider integration while developing.
Use your runtime's debugger, request logs, or provider tooling when the behavior is unclear instead of relying only on repeated print statements.
2.6. Design and testing
Keep the tests from Level 1.
Add at least one integration test or documented manual verification that demonstrates the operation working against the real provider.
Do not make every test depend on the real provider.
Provider-backed tests may depend on:
network availability;
credentials;
test account state;
provider availability.
That makes them useful for integration verification, but less suitable for testing every piece of application behavior.
You will address this separation more explicitly in later levels.
2.7. Team integration
Provider integrations often contain assumptions that are not obvious from the code alone.
Before merging, another teammate should review:
which provider endpoint or SDK operation is used;
how authentication is configured;
how provider data is translated into your public response;
any assumptions made about provider identifiers or behavior;
the instructions for running the integration locally.
At least two members of the team should be able to run the operation against the provider.
2.8.You don't need these yet
You are not required to:
support more than one real provider;
define the final provider-independent interface;
use dependency injection;
replace the provider with a fake implementation in tests;
normalize every provider-specific concept;
handle every provider failure;
implement retries;
support collections or pagination.
Focus on getting one real request through the entire system.
2.9. When you're done
This level is complete when:
the operation from Level 1 uses your real provider;
its public request and response contract still behaves as documented;
provider-specific data is translated before it reaches the caller;
credentials are kept outside the repository;
another teammate can follow your documentation and run the integration;
Your team has verified the operation end to end with a real test account.
You now have the first complete path through your service:
caller → your service → real provider → your service → caller
In the next level, you will define the boundary between your application and that provider.
