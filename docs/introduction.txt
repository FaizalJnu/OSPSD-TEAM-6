Homework 1:  Build, Test, and Release a Backend Service

TA repo flag: https://github.com/nyu/oss-taapp-example 
1. Overview
For this course, you are tasked with building an open-source agent related to the verticals listed below (TA’s note: this could be anything of your choice, last semester I built an agent that can store files to cloud storage platforms like AWS and GCP right from your terminal or Slack). 
The primary goal of this assignment is to build a small backend service for the agent in a way that another developer can use and contribute to. You will select a client vertical category, define its “interface”, build a concrete “implementation” of your interface by connecting your service to a real provider and implement a useful workflow (you should be able to perform basic operations such as Create, Read, Update, and Delete).
Pick your vertical: OSPSD Fall '26 - HW1 Pick'Ems
Each team will choose one of the following verticals for your clients and your choice of implementation. 
Calendar (e.g., Google Calendar, Outlook, Cal.com etc.)
Chat (e.g. Slack, Discord, Microsoft teams, Telegram, Zulip etc.)
Document Storage (e.g. DropBox, Google Drive, Onedrive, Box, etc)
Issue Tracker (e.g. Linear, Trello, Jira, Asana, Basecamp etc.)
Email (Gmail, Resend, Fastmail, HEY, etc)


We'll open the sign-up sheet sometime within 24hrs of the teams being finalized for fairness. 
Once your team has chosen a vertical, define the public API for the service. and build a small working version. By the end, a new developer should be able to set up and use your service by following your documentation. Running it locally with a test account is sufficient. This will set up your foundation for all future homeworks. As you go on in the course, you will build on top what you create here.


 The main learning goals are to:
Translate incomplete requirements into consistent, testable behavior by asking questions, stating assumptions, and defining what success looks like.
Build a small but complete backend feature connected to a real provider and keep the service’s public behavior separate from the details of the external provider it uses.
Learn how to design good interfaces, understand how interfaces impact implementations and build a chosen concrete implementation that you can “inject” through Dependency Injection. 
Handle real integration problems, including invalid input, collections of results, repeated requests, and provider failures.
Write tests for expected behavior and edge cases, then use failing tests to investigate bugs.
Collaborate through issues, implementation, review, integration, and release.
Make technical decisions under time constraints and explain their consequences.
Take responsibility for code contributed by teammates, libraries, and coding agents.
1.1. Scope and Design Freedom	
Complete the workflow for your chosen category and all shared requirements in this handout. Optional extra-credit extensions appear at the bottom of the handout. You choose endpoint names, internal interfaces, representations, module organization, and supporting tools. Where this handout leaves a choice open, choose a reasonable behavior, document it, and test it. Your choices must preserve the required behavior.
The examples in this handout illustrate observable results; they do not prescribe a directory layout, class hierarchy, endpoint naming convention or anything else. Use ordinary Python modules, functions, and classes when they solve the problem. Introduce an abstraction or another service when you can explain the concrete benefit.
FastAPI and a real provider integration are required. Provider SDKs and established libraries are allowed. Your service must do real work against the provider. Test doubles support repeatable testing; the final demonstration must also show the required workflow against the actual integration. For all categories, provider limitations must be identified early and reflected accurately in the API.
Choose a small scenario that crosses the whole system. For example, if you’ve chosen the document storage vertical, upload one document through your API, retrieve it through your API, and compare its bytes. For chat, send a message and find it in the intended conversation. Build this path early, then expand its behavior and tests.
Use a test bucket, workspace, calendar, or project containing data your team may change. Document the setup, permissions, provider restrictions, and cleanup instructions. Verify access before assigning substantial implementation work. Raise access or cost problems with staff early.
2. Teamwork
2.1. Start together
Read the handout as a team, choose the category and provider, and set up the shared repository, development instructions, and CI early and in a way it’s reproducible by anyone. Some tips:
Record the supported Python version and the installation steps.
Pin or lock dependency versions so any teammate, or a new developer following your documentation, can reproduce the environment exactly.
Document how to obtain and configure test credentials for your chosen provider. Running locally with a test account must be enough to set up and use the service;nothing else should be required.
Keep credentials, generated files, temporary data, and unrelated changes out of the repository unless they serve a documented purpose.
By the first working version, every member of the team should be able to run the service and fast tests. Post questions about unclear requirements in the slack #help channel. Shared answers help other teams and make expectations consistent. If you haven’t noticed already, things are kept intentionally vague to encourage asking questions out loud! 
2.2. Agree on how you will work
We recommend creating a team agreement document inside the docs folder in your github repository that everyone contributes to and accepts. Even if you choose not to (which is completely ok!), it helps having a discussion around  aspects such as:
availability and expected effort
communication channels
reasonable response times
decision-making
review turnaround
what happens when someone is blocked or unavailable
Decide how coordination responsibilities are assigned and how disagreements are resolved. Update the agreement when experience shows it needs to change.
Raise team problems early. Staff can help with access issues, technical choices, uneven participation, and conflicts. Sensitive concerns may be discussed privately.
2.3. Dividing Work
Before dividing work, agree on the interface and contracts before implementing dependent pieces. Discuss changes with the teammates who use those contracts. Prefer tasks that deliver observable behavior and include their tests and documentation. 
Feel free to use an issue tracker such as Linear, GitHub Issues, or a plain markdown file to track the dependent pieces (ref: John Carmack .plan Archive). You will learn later in class how to properly divide work, so until then a naive approach should expose you to the difficulties of breaking down a complex task and dividing it between the team. You can take this a step further by assigning an owner, a deliverable, a rough effort estimate, a reviewer, and dependencies on other work for each substantial task. 
Use the teammate’s work as an exercise as real practice reading and changing someone else's code. Coordinating a release or writing docs counts as much as implementing or testing. Ideally, every module comes with a spec and dedicated educational material for understanding that spec and the important parts of its implementation.
	Pro-Tip: Aim to write code that’s similar to good Haskell and OCaml modules: the type definitions and function signatures should give an overview, while the documentation comments should teach you what else you need to know. The module structure and types structure the learning materials.
2.4. Agree on and practice your release lifecycle
Throughout this entire “sprint”, you must adhere to the guidelines talked about in class regarding testing and development workflow. Decide how work moves from an idea to a usable release. Choose a cadence that fits the team: short planning cycles or a continuously prioritized queue are both reasonable. Planning periods and release dates may differ (TA’s note: I highly recommend reading about the software release lifecycle and how real companies ship software to select an approach that works best for the team).
In your AGENTS.md or in a similar doc, record:
How work is selected, work in progress is limited, and unfinished or urgent tasks are handled.
How issues move through implementation, review, verification, and release, with an owner for each transition.
Which checks and human reviews are required before merging and releasing.
How versions are named and compatibility changes communicated.
Who coordinates and verifies a release, and how a defective release is handled.
Use the workflow throughout the assignment. Link issues to pull requests and included changes to releases. Make it clear when work is merged, released, and, if applicable, deployed. Automate transitions where useful, while keeping their meaning accurate.  
2.5. Publish a review release and a final release
Publish at least two GitHub Releases, corresponding to the existing review and final milestones. Choose and explain a version scheme. For example, use v0.1.0-rc.1 for review and v0.1.0 for the final submission. The examples are not required names, and a completed homework need not be version 1.0.
A Git tag identifies the source revision. A GitHub Release adds release notes and any distributable assets associated with the tag. A runnable source release is sufficient for HW1.
For each release:
Select the exact commit and run the required checks. Verify the behavior included in the release and identify incomplete scope. The review release may have unfinished requirements, which must be visible in its notes; the final release is expected to satisfy the complete core.
Create and push an annotated Git tag for that commit. Have a teammate verify setup and a representative workflow from a fresh checkout of the tag.
Write release notes covering user-visible changes, relevant issues or pull requests, breaking changes, setup or configuration changes, and known limitations. Review automatically generated notes before publishing.
Publish a GitHub Release using the verified tag, with links to verification and CI evidence. Mark the review release as a prerelease. Use a different coordinator for the final release.
Keep published tags attached to their original commits. Corrections go into a new version. If a release is defective, explain whether users should return to an earlier version or wait for a fix, and identify state or configuration that reverting code would not restore.
After the review release, record one observation about the workflow and any adjustment you make. Use existing issues, reviews, and releases as evidence of how the process worked.

3.1. Review another team
You will be reviewing your sister team's implementation of the same vertical after the second milestone. Primarily responsibilities of each team include but not limited to::
Read its contract and code map, follow setup instructions, run the fast tests, and trace one workflow through state changes and provider calls
Consult relevant tests and history to understand unfamiliar decisions.
Complete the main workflow using the documentation only. 
Check behavior, tests, design, failure handling, compatibility, and relevant security or performance concerns. 
You will share feedback through Github Discussions or leaving comments in the open PR. Some examples of feedback you can expect to give are listed below:
Labelling comments as blocking issues, design concerns, questions, or optional suggestions. 
Tie a blocking issue to a requirement or a concrete defect. 
Give a counterexample of why something is not implemented correctly, and suggest a next step. 
Point out effective designs and tests when that feedback will be useful. 
Report where you struggled when you tried to follow the documentation to set things up.
This is a great learning opportunity to see how other engineers work and reproduce their work locally. Giving and taking honest feedback levels you as a software engineer and you especially learn how to discern the good feedback from the bad. As the popular idiom goes, “chew the meat and spit out the bones”. 
3.2. Revise in response to feedback
Respond to every substantive review comment with a fix or a reasoned explanation. Link the relevant change or follow-up issue. An unresolved required behavior remains incomplete even when it has a follow-up issue.
Use the usability feedback to make one justified improvement to behavior or documentation. Explain it in the relevant pull request. If reviewers disagree about a requirement, ask staff to clarify it.
You may learn from another team's design and discuss general approaches. Your submitted implementation must be your team's work; peer review does not authorize copying another team's solution. 
4. Deadlines, slack days, and extensions
4.1. Ordinary extensions
Each team has 10 slack days for the semester. This is one shared balance, not 10 days per member or per assignment.
One slack day extends a deadline by 24 hours. Slack days are used in whole-day increments.
A team may use at most two slack days for a single deadline.
For HW1, slack days may be used on the review-release deadline, the final-release deadline, or both. Using one day on each costs two days from the shared balance.
Request the extension before the original deadline by sending a Slack message to the TA or course staff. Include the team members, assignment milestones, and number of days requested. Make sure the team agrees on using its balance.
Requests within the available balance and per-deadline limit do not require a personal explanation. Staff record the request and confirm the adjusted deadline and remaining balance.
Slack days provide room for workload peaks, minor illness, travel, and other interruptions. Use the time to recover, seek help, and make a realistic plan.
Extending a release deadline does not automatically move another team's review deadline, a scheduled demonstration, or a meeting. Notify staff early when an extension affects a shared activity so they can coordinate the schedule. The first working-version checkpoint is intended to reveal progress and blockers; attend or submit the current state, and ask staff if attendance or submission is not possible.
4.2. Submission cutoff and late work
We assess the work pushed and submitted by your applicable deadline, including any timely requested slack days or separately approved extension. Submit the release link, tag, and matching commit identifier so the revision is unambiguous.
Continue development in new commits if needed, but do not move a submitted tag to include later work. Changes after the cutoff are not part of that submission unless staff authorize them. Without an extension, the original deadline remains the cutoff; a later push does not automatically replace the on-time work.
4.3. Circumstances beyond the ordinary allowance
Additional time after the balance is exhausted, or beyond two days for one deadline, requires instructor approval. Contact staff privately as early as possible with the situation and a proposed next step. If an emergency prevents advance notice, contact staff as soon as you are able.
Significant illness, emergencies, and ongoing access or support needs should be discussed with staff rather than handled solely by spending slack days. Staff will explain any applicable course or university process. Keep sensitive information out of public channels and the team repository.

6. Evaluation
We assess the published requirements and the evidence behind your work through PRs. Reasonable implementations can make different design choices.

What we look for

Separation between API and implementation. Clear responsibilities, controlled state and resource ownership, useful types, and changes that teammates can understand.

A teammate, or the course staff reviewing your PR, can read it and know what it does, who owns what state, and why it's shaped that way.

Tests derived from contracts, meaningful failure cases, reproducible investigations, and accurate claims about what has been established.

Grading will revolve around thoughtful decisions and working software that meets the assignment. Document incomplete work honestly and explain priorities. Optional features do not replace the required behavior, and the number of tools, files, commits, or features is not a measure of quality. 
Note when using agents, you will be held accountable for the complexity and the LoC. You will be spending your careers fighting the complexity demon that wakes you up at 3 in the morning so choose your abstractions carefully. Be explicit in the PR if the code was generated with AI. Your first code won’t be your last so feel free to write and throw away code as much as you see fit. Points will be deducted for unreasonably high LoC with no purpose. 
We would like to see how you reason about the problem and the code, so write the commit messages and PR yourself if possible. It helps you think on a meta-level on how you implemented something and you’ll be more in touch with the code, especially if you heavily rely on coding agents. This way you won’t lose context and can quickly re-iterate parts of the codebase without having to on-board yourself every time you want to change something. 
Use the assignment to build something you can explain with confidence: what users needed, what you built, what went wrong, how you know it works, and what you would change next. Here are some tips on how you can achieve this:
Describe the important modules and types, their responsibilities, dependency direction, and ownership of state. Identify boundaries that must be preserved, such as keeping provider SDK types inside the integration code.
Show how a request passes through input validation, application decisions, provider interaction, and response construction. A paragraph or a small diagram is sufficient if it makes the path clear. Explain what FastAPI, your application, and the SDK each do in the docs.
For a non-obvious representation, explain how it corresponds to the public model and which states are valid. Enforce important invariants where state changes. Use internal assertions where they help expose programming errors; validate untrusted input through ordinary error handling.
Choose boundaries based on related behavior and expected changes, then evaluate an abstraction by what a caller must understand, what it hides, and the cost of maintaining it. File count, class count, and the number of named design patterns are not success measures.
6.1. Justify one substantial decision
Explain:
What problem are you solving, and which constraints matter?
What alternatives did you consider?
What evidence supports the choice?
What are you giving up, and what remains uncertain?
What would make you revisit the decision?
Evidence may be a provider capability, a test, an experiment, a measurement, or an explicit workload estimate. Distinguish observations from assumptions.
6.2. Explain the cost of one operation
Choose an operation whose work grows with input size. Identify the relevant data structures, local time and memory costs, and number of provider calls. State your assumptions and use asymptotic notation where useful.
For listing, distinguish entries returned from entries fetched or inspected. Identify work delegated to the provider and what you cannot infer about its implementation. A slow request alone does not establish whether the cause is local computation, serialization, I/O, or provider latency.
6.3. Extend a teammate's feature
A teammate who did not lead the original implementation of a feature should extend it through a normal pull request if and only if there’s room for improvement. Before editing, identify the expected behavior and the boundary that should contain the change. 
Afterward, explain which modules or interfaces changed, why the change spread, and which tests demonstrate the result. Preserve existing guarantees and document intentional contract changes. Use this handoff to evaluate the design of your system. 
You could provide a counterfactual on why you couldn’t extend a feature. This helps you exercise what parts of code need improvement and what doesn’t.

7. Coding agents, External Code, and Contribution Hygiene
Coding agents are allowed. Every submitted change has a student owner who can explain, verify, and maintain it. The same standards apply regardless of how the code was/ produced.
Include an AGENTS.md that helps a new contributor or an agent work safely in the repository. Cover the code map, important architectural constraints, setup and check commands, test boundaries, and relevant contribution rules. Link existing documentation instead of maintaining conflicting copies. If you support another tool's instruction file, keep shared rules consistent.
Give agents bounded tasks with a contract and acceptance criteria. Review the implementation, tests, new dependencies, and changes to configuration or checks. Verify claims about provider behavior against the integration and its documentation. Keep changes focused enough for a teammate to review.
Agent-generated tests must be meaningful and catch plausible errors. Human review remains required for substantive changes. Agent review can provide additional evidence, and the student owner remains responsible for the final decision.
Preserve checks unless the team has a documented reason to change them. Remove unused code and dependencies, maintain clear names and public interfaces, and keep unrelated edits out of feature changes.
Use established libraries where they help. Attribute external code and significant adaptations, respect applicable licenses, and document contributor expectations. Choose a license deliberately if you publish the repository for reuse; public visibility alone does not communicate reuse permissions. A public repository or package-registry publication is not required for HW1.
You may use this sample AGENTS.md to get an overview on the types of rules you can impose on both developers and agents alike (TA’s note: DO NOT blindly copy the whole thing, It might over-engineer the entire assignment and may drift from what you need to accomplish. Use the resources appropriately and responsibly).
