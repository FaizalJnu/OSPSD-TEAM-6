1. Optional extensions
Once the core works, choose an extension that fits your product and available time. Define its contract and limits before implementing it. Apply the same design, testing, review, and release standards.
Extensions must preserve the core guarantees. Distinguish partial effects after a network interruption from the unchanged-state guarantee for locally rejected input.
You may propose another extension with comparable engineering depth. Discuss an uncertain scope with staff before making a substantial commitment.
Extension
What to implement and demonstrate
Caching
Reduce repeated provider work. Define cache keys, expiry, invalidation, and permitted staleness. Demonstrate a hit, expiry or invalidation, and the resulting provider-call count. Use something like Redis.
Idempotency keys
Handle repeated and overlapping creation requests within documented guarantees. Define key scope, retention, conflicting payloads, restart behavior, and uncertain provider outcomes. Show that the promised logical action is not duplicated.
Conditional updates
Have two clients read the same version, then prevent or explicitly reject a stale overwrite. Explain how the check and write remain consistent with the guarantee.
Streaming
Transfer large content with bounded memory. Measure memory, interrupt a transfer, and demonstrate cleanup and any remaining partial effects.
Background work
Accept work, expose status, and recover from an interruption. Define what acceptance guarantees, what survives a restart, and how duplicate execution or external effects are handled.
Overload protection
Use a bounded queue, concurrency limit, rate limit, or another justified control. Increase controlled load and show predictable behavior and bounded resource use. Redis is an option if a shared state is needed.
Release and recovery
Deploy a release and recover from a controlled release failure. Have a teammate follow the instructions; explain access protection and state or configuration compatibility. Use tools like graceful shutdown and logging to showcase error handling.

Distinguish what your team implemented from what a provider or library supplies. A tool's advertised guarantees are not evidence that your integration preserves them.
