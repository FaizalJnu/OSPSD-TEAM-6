Level 4: Inject the Provider Implementation
Your service now has a provider-independent interface. The next step is to make the concrete provider implementation replaceable.
4.1. Your goal
Refactor your service so that application logic receives an implementation of the provider-independent interface instead of creating or importing the concrete provider directly.
Your real provider should still power the service when you run it normally.
Your tests should be able to supply a different implementation.
4.2. What should happen?
Your service may currently look conceptually like this:
HTTP request
    ↓
application operation
    ↓
provider-independent interface
    ↓
your client vertical category implementation
However, if the application code itself decides to construct your chosen implementation, the dependency is still fixed.
By the end of this level, the implementation should be supplied from outside the code that uses it:
application startup
        │
        │ supplies implementation
        ▼
application operation
        ↓
provider-independent interface
        ↓
real provider implementation
A test should be able to supply another implementation:
test
  │
  │ supplies implementation
  ▼
application operation
        ↓
provider-independent interface
        ↓
controlled test implementation
These diagrams describe responsibilities, not required classes, modules, frameworks, or file structures.
4.3. Specification
Application logic must depend on the provider-independent interface defined in Level 3.
The concrete provider implementation must be supplied to the application rather than constructed directly by the code that uses it.
Your implementation must satisfy the following:
the public operation from previous levels still works against the real provider;
application logic depends on the provider-independent interface;
application logic does not construct the concrete provider it depends on;
provider-specific SDK types remain behind the provider boundary;
tests can substitute a controlled implementation;
those tests do not require network access or real provider credentials.
How your team accomplishes this is a design decision.
You do not need a dependency-injection framework.
4.4. What you need to think about
Before implementing, agree as a team on:
Where is the real provider implementation created?
Which component is responsible for supplying it to the application?
Which code is allowed to know which concrete provider you selected?
Which code should depend only on the interface?
How will tests supply a controlled implementation?
What state, configuration, or credentials does the real implementation need?
Is the interface still small enough that creating a test implementation is straightforward?
There should be a clear answer to the question:
Where does the application choose its concrete provider?
Try to keep that decision localized.
4.5. Design and testing
Create a controlled implementation of your provider-independent interface for use in tests.
It should return predictable values without contacting the real provider.
Use it to test the application behavior you implemented in earlier levels.
For example, a test implementation might be configured so that:
getResource("resource-123")
returns:
Resource {
    id: "resource-123",
    name: "Example resource"
}
Your application test should exercise the same behavior it would with the real provider.
The test implementation is not meant to reproduce the provider. It only needs enough behavior to support the test.
Keep your real-provider integration verification from Level 2 as well.
You should now have two different kinds of confidence:
controlled implementation
        ↓
application behavior tests

real implementation
        ↓
provider integration verification
4.6. Team integration
This dependency boundary will affect most features you add later.
Review it as a team before merging.
Your team should be able to explain:
where the real provider is created;
where it is supplied to the application;
which code knows the identity of the provider;
which code depends only on the interface;
how a test substitutes another implementation;
what would need to change if the concrete provider implementation were replaced.
At least one teammate other than the primary author should review both the real wiring and the test substitution.
4.7. You don't need these yet
You are not required to:
support multiple real providers;
allow users to switch providers at runtime;
build or adopt a dependency-injection framework;
create a plugin system;
dynamically discover implementations;
mock the provider SDK directly;
reproduce the provider's behavior in your test implementation;
handle every provider failure.
Use the smallest design that makes the dependency replaceable and testable.

4.8. When you're done
This level is complete when:
the existing public operation still works against the real provider;
application logic depends on your provider-independent interface;
the concrete provider implementation is supplied from outside the code that uses it;
tests can replace the real provider with a controlled implementation;
those tests require no network access or provider credentials;
your team can identify where the real provider is selected and explain how that dependency reaches the application.
In the next level, you will define how your service behaves when requests or provider operations fail.
