Part I: Working Software Rubrics
50 points
Does your software do what you say it does, and can another developer reproduce that without your help?
How to use this checklist
Review the service as a team using the release you intend to submit. Start from a clean checkout, follow the setup instructions, exercise every required operation, reproduce the applicable failure cases, and run the documented checks.
Use existing code, tests, API documentation, verification records, CI runs, and releases as evidence. Link the relevant material from your submission. You do not need a separate report or duplicate documentation.
Scoring. Follow the point breakdown and scoring rule under each item. Where points are divided among operations or implementations, each earns its share by demonstrating the stated condition. Partial credit comes from the checks and shares completed. For a deduction, the grader will identify the unmet condition and a concrete example.
Review scope. Graders will assess the submitted revision, follow its setup instructions, check each required operation against its public contract, and inspect applicable failure handling. They will also examine automated tests, real-provider verification, CI results, and release records.
Implementation freedom. Within the assignment’s requirements, your team may choose its repository structure, supporting libraries, API client, and documentation tools. Different implementations can earn full credit. Points depend on demonstrated behavior and reproducible verification, rather than the grader’s preferred implementation style.
1. Required behavior and contracts
    16 points
1.1. Make every required operation work  8 points
Implement every operation your team committed to for the assignment. A grader should be able to call each operation through the public API and receive the documented result.

What to verify

Update

Other action
The observable effect matches the documented promise.

Check the response status and contents as well as any promised state change. A successful HTTP status alone does not establish that a write worked. For collections, check the returned records and the collection behavior your contract promises
Scoring: An operation earns its share when the response and observable result satisfy its contract.
1.2. Each operation has an accurate public contract  4 points
For each required operation, verify that the documentation, examples, and implementation agree on:
1 point: HTTP method and route.
1 point: Inputs, including required and optional fields and applicable constraints.
1 point: Successful status, response fields, and their meaning.
1 point: Side effects and applicable failure responses.
Scoring: Divide each point equally among required operations. Existing API documentation and linked explanations are sufficient; do not duplicate them in another document.

Scoring: Within each category, divide its point equally among the applicable implementations. Missing handling is not an exclusion.


2. Real provider integration
    8 points
2.1. Every required operation performs real provider work  4 points
Run each required operation through your HTTP API against the selected provider using a test account.
Verify that the returned data or external effect comes from the real integration. A fake provider, hard-coded response, or local-only implementation does not satisfy this check.
Keep a runnable integration test or a documented manual procedure showing the request, expected result, and observed result. For writes, establish the external effect through an appropriate provider observation or subsequent read.
Scoring: Divide 4 points equally among required operations.
2.2. Translate provider data before returning it  2 points
Inspect the provider result and the corresponding public response. Verify that the service selects, converts, or maps the data into its documented model.
Callers must not need to interpret raw SDK objects or undocumented provider structures. Ordinary domain names such as id, event, and message may match the provider’s vocabulary.
Scoring: Divide 2 points equally among required operations.
2.3. Credentials are supplied safely and out of the repository  2 points
1 point: The service obtains secret values through external configuration rather than hard-coded source values.
1 point: Submitted repository content contains no provider credentials, tokens, or other secret values.
Configuration examples with placeholders and non-secret defaults are allowed.

3. Testing and verification
     12 points
3.1. Every required operation has a public success test  4 points
Run a test that calls each operation through the HTTP API and checks its promised successful behavior.
Assert the status and meaningful response contents. For writes, also check the resulting controlled state or the provider interaction required to produce the effect. Testing only an internal helper is insufficient.
Scoring: Divide 4 points equally among required operations. A test earns credit when its assertions establish the required behavior, including when it currently fails because it exposes a service defect.
3.2. Required failure cases have meaningful tests  4 points
Provide automated tests for the four failure categories in Section 1.
Each test must:
Reproduce the failure using controlled input or provider behavior.
Assert the public status, error code or type, and response structure.
Check the absence of a provider write when rejecting locally checkable invalid input.
Use the same applicability and shared-implementation rules as Section 1.
Scoring: Each category is worth 1 point, divided equally among its applicable implementations. Staff-approved exclusions receive credit here as well.
3.3. Run your normal tests without the real provider  2 points
1 point: The documented fast-test command runs without real provider credentials.
1 point: The fast suite runs without live network access, using controlled provider behavior.
Real-provider tests must be separately selectable. They must not run unexpectedly as part of the fast suite.
3.4. One test detects a plausible defect 2 points
Choose one important guarantee and demonstrate that a test detects an implementation mistake.
1 point: Record the defect and show the relevant assertion failing because the behavior is wrong.
1 point: Show the same test passing after the defect is fixed or the temporary change is removed.
An actual bug and its regression test can satisfy this check. Otherwise, temporarily introduce a small behavior defect and restore the correct implementation before merging.
A syntax error, import failure, or broken test setup does not establish that the test checks the guarantee. Record the evidence in an existing PR. Note that a meaningful failing test can earn testing credit, while the unfixed behavior and failing CI lose points under their respective checks

4. Setup and documentation
    8 points
4.1. A fresh checkout can be installed and started  3 points
Use the submitted tag in a new directory and a clean environment. Follow the repository instructions without relying on an existing virtual environment or undocumented local files.
1 point: The supported Python version and documented dependency installation work using the submitted dependency declarations or lockfile.
1 point: After completing the documented configuration, the service starts with the documented command.
1 point: A documented public request reaches the running service and returns the expected result.
4.2. Provider configuration is documented  2 points
1 point: Required configuration names, their purposes, and where to supply their values are documented.
1 point: Test-account setup, credential acquisition, required permissions, and applicable provider restrictions are documented.
Another developer should be able to obtain their own test credentials. Secret values must not appear in the instructions.
4.3. Usage examples are runnable 2 points
1 point: Each required operation has a complete request example, including how to obtain or replace any sample identifiers.
1 point: Examples state the expected response or effect and explain preparation and cleanup where needed.
Examples may use curl, Swagger UI, Bruno, Postman, or an equivalent client. A sequence may cover several operations.
Scoring: Divide each point equally among required operations.
4.4 Check commands are documented 1 point
Provide the command or sequence of commands for the fast tests, linting, and type checking. Separately identify the command or procedure for real-provider verification and its prerequisites.

5. CI and releases
    6 points
5.1. Required checks pass in CI on the submitted commit  2 points
1 point: The fast automated tests run and pass.
1 point: Linting and type checking run and pass.
Link the CI run for the exact submitted commit. Document equivalent local commands. Live-provider tests do not need to run in CI.
5.2. The final release identifies the submitted revision  2 points
The final GitHub Release points to an annotated tag and a matching commit identifier included in the submission. Keep the published tag attached to that commit; later corrections require a new version.
5.3. The review prerelease is available  1 point
Provide the earlier GitHub Release used for the review milestone, marked as a prerelease and identifying its tagged revision.
5.4. Release notes describe the release accurately 1 point
For both releases, identify included behavior, known gaps, and relevant setup or compatibility changes. State when there are no known gaps or relevant changes. Existing issues and PRs may supply details through links.

Part II: Engineering Quality Rubrics
50 points
Can another engineer understand, change, debug, and review your team’s service?
How to use this checklist
Review the service as a team. Trace a request through the code, inspect the provider boundary, reproduce a controlled failure, and read the PRs and reviews that explain your work.
Use existing code, documentation, PRs, and review threads as evidence. A short explanation beside the relevant implementation or change is sufficient; you do not need a separate design report.
Scoring. Award points when its stated condition is demonstrated; otherwise award zero. Partial credit within a category comes from completing its separate checks. For a deduction, the grader will identify the unmet condition and a concrete example.
Review scope. Graders will inspect the public contracts, trace a representative operation through its successful and failure paths, examine provider setup, and review linked changes and feedback. They may inspect other required operations to verify that the same guarantees hold across the service.
Design freedom. No particular directory layout, class hierarchy, dependency-injection framework, or documentation tool is required. A deduction must concern a condition below, rather than the grader’s preferred coding style.
6. API consistency
8 points
Part I checks whether each operation satisfies its contract. This section checks whether the operations form one coherent API.
6.1. Shared concepts have consistent names and representations 3 points
Compare fields that describe the same domain concept across requests and responses.

Check
What to verify
Points
Names
The same concept uses the same terminology in comparable contexts. Different names identify an actual distinction.
1
Types and units
Shared values use compatible types, formats, units, and meanings. For example, a timestamp does not silently change timezone conventions between operations.
1
Identifiers
An identifier returned by one operation can be used by related operations as documented, with the same meaning and scope. Any required conversion or additional parent identifier is explicit.
1

Make the API describe your domain, not your provider. Use concepts meaningful to callers of your service. Callers should not need to construct SDK objects or understand undocumented provider payloads. Names such as event, message, and file may match the provider because they also describe your domain. Context can justify different names: id inside an event and event_id in a route parameter can clearly identify the same concept.
Keep the public surface as small as the assignment needs. Do not add endpoints, parameters, response fields, configuration options, or abstractions simply because the provider supports them. Every public feature becomes something callers may depend on.
Scoring: Award each point when the convention holds across the applicable required operations. A deduction must identify conflicting uses of the same concept. Check only concepts the service actually exposes; timestamps or identifier-based workflows are not additional requirements.
6.2. Related operations follow shared conventions  3 points
Compare operations that perform similar work or exchange the same resource.
1 point: Related routes, HTTP methods, and successful statuses follow a consistent approach. Differences correspond to different behavior.
1 point: Shared inputs have consistent requiredness, defaults, and constraint meanings unless the operation’s purpose requires a difference.
1 point: Related success responses represent comparable data consistently, including nesting, wrappers, and collection items.
For example, a compact listing and a detailed resource response may contain different fields. Their shared fields should retain the same meaning. A delete response does not need to resemble a create response.
Scoring: Award each point when related operations follow the convention or have an explained semantic reason for differing. No particular route style, response wrapper, or collection feature is required.
6.3. Equivalent failures have equivalent public meanings  2 points
Reuse the applicable failure cases from Section 1. Compare their public responses across operations.
1 point: Errors use a consistent structure and representation for the machine-readable code or type.
1 point: Equivalent failure conditions use consistent codes and HTTP-status meanings. The same code does not describe unrelated failures.
A client should not need to read error.code for one operation and parse a message string for another operation’s equivalent failure.
Scoring: Award each point when the convention holds across applicable error-handling implementations. Staff-approved exclusions from Section 1 apply here as well.
7. Code readability and state ownership  8 points
Follow a required operation through its implementation. Check whether another teammate can understand its responsibilities, identify its effects, and change its rules.
7.1. Names and functions explain the work 3 points
1 point: Variable names and types describe the values’ purpose and meaning. Units are explicit where confusion is possible. A value called size_bytes contains bytes; a collection called messages contains messages.
1 point: Functions perform an identifiable job. Their steps serve that job, and unrelated behavior is separated so it can be understood and changed independently.
1 point: Side effects are apparent from the function’s name, contract, or call site. A caller can identify operations that perform network I/O, write files, or change application or provider state.
A function may coordinate validation, a provider call, and response construction to perform one application operation. It does not need to be split merely because it contains several steps.
For example, a helper presented as local input validation should not silently upload a file.
Scoring: Divide each point equally among required operations. Inspect shared code once. A deduction must identify the misleading name, unrelated responsibility, or hidden effect; function length alone does not establish a problem.
7.2. State and resources have clear owners  3 points
For each operation, follow the state and resources it uses.
1 point: Identify who owns the relevant state, how long it lives, and which code may change it. Distinguish request data, deliberately shared application state, and provider-owned state.
1 point: Mutations preserve the stated validity rules, and temporary request or test data do not accidentally carry into unrelated invocations.
1 point: Resources created for execution or verification have an identifiable lifetime and cleanup path, including when an operation fails.
Check applicable clients, files, temporary directories, and test resources. A long-lived client is acceptable when its application lifetime is clear. Resources created as the operation’s intended result remain according to the public contract.
Scoring: Divide each point equally among required operations. Shared ownership and cleanup mechanisms are inspected once. A stateless application or an operation without cleanup obligations earns credit when the implementation establishes that those obligations do not arise.
7.3. Explanations and retained code match the current design 2 points
Inspect the code and supporting explanations along the same operation paths.
1 point: Comments and docstrings accurately explain contracts, assumptions, invariants, provider restrictions, or non-obvious decisions where that information is needed. They remain correct after changes to the implementation.
1 point: Refactoring has not left abandoned implementations, commented-out code blocks, unused direct dependencies, or obsolete instructions that obscure the supported implementation.
A comment explaining why a provider requires a particular conversion is useful. A comment repeating an obvious assignment does not establish understanding.
An accurate TODO describing remaining work is acceptable. Tests, development tools, and documented utilities have legitimate purposes even when production requests do not invoke them.
Scoring: Award each point independently for the reviewed code. Straightforward code can earn full comment credit without additional comments. A cleanup deduction must identify the obsolete or unused item and establish that it has no current purpose.
8. Provider boundary and dependency injection 10 points
Inspect what crosses the provider interface, where provider details are interpreted, and how real and controlled implementations reach the application.
8.1. The provider-independent interface has an explicit contract 2 points
Read the interface used by the application and compare it with its implementations.
1 point: Inputs and results use domain values or types whose meaning can be understood without interpreting SDK objects or undocumented provider structures.
1 point: Required interface operations have an accurate description of purpose, inputs, results, side effects, and assumptions callers may rely on.
For example, an interface may accept a resource identifier and return the resource information the application needs. Ordinary domain terms may match the provider’s vocabulary.
Scoring: Divide each point equally among required operations. Types, signatures, docstrings, and linked documentation may establish the contract together; a separate interface report is unnecessary.
8.2. Provider details are interpreted inside the integration boundary  3 points
Follow a provider call and inspect what returns to the application.
1 point: SDK calls and provider-specific request construction occur in integration code. Startup code may create and configure the dependencies it supplies.
1 point: Provider results are selected, converted, or mapped before crossing the interface. Application logic does not inspect SDK attributes or raw provider response layouts.
1 point: Provider-specific exceptions and quirks are interpreted behind the boundary. Application code handles the service’s defined outcomes rather than matching SDK exceptions or parsing provider error messages.
Inspect the internal result before HTTP response construction. A correctly shaped public response alone does not establish this boundary.
Scoring: Divide each point equally among required operations. Shared adapters and translation helpers may establish the condition for several operations.
8.3. Application logic receives its provider implementation 3 points
Trace the normal service wiring from startup or dependency resolution to the application operation.
1 point: Application logic uses the provider-independent contract and does not depend on the concrete provider’s class, SDK, or additional methods.
1 point: The implementation is supplied to that logic. The code using provider behavior does not construct or look up a hard-coded concrete provider.
1 point: The normal wiring identifies where the real implementation is selected, created, and supplied. That selection is outside the application logic using it.
Constructor arguments, function arguments, and FastAPI dependencies are acceptable approaches.
Scoring: Divide each point equally among required operations. A shared setup path is inspected once and earns credit for the operations it correctly supplies.
8.4. Tests replace the implementation at the team’s interface  2 points
Run an existing application test using a controlled provider implementation.
1 point: The controlled implementation supports the interface behavior exercised by the test, including compatible inputs, results, and configured failures.
1 point: The test supplies that implementation and exercises the same application decisions used with the real provider. Substitution does not require editing application logic or bypassing it through test-only branches.
Patching an SDK’s network call by itself does not demonstrate substitution at the team’s interface. The controlled implementation only needs enough behavior to support the tests.
Scoring: Divide each point equally among required operations. Section 3.3 separately awards credit for running without network access or real credentials.
Self-review: Follow one change
Use an existing change from your team’s work, such as changing an input constraint, adding a response field, or translating a provider error.
Before inspecting the diff, identify where the behavior belongs. Then inspect every changed file:
What responsibility required this file to change?
Did the same application rule need to be updated in several places?
Did a provider detail escape into application logic?
Which tests establish the new behavior and preserve existing guarantees?
Several changed files may be appropriate. A response-field change can legitimately affect a model, mapping code, documentation, and tests. Explain the responsibility of each change.
Use the existing PR as evidence. If no useful change is needed, trace a hypothetical change through the current code; do not manufacture a refactor.

9. Failure diagnostics  6 points
Reuse the controlled failures from Part I. Inspect what an engineer can learn from the resulting logs.
Ideally, you could reproduce a controlled failure and ask a teammate to use the response and logs to identify the failed operation, whether the provider was involved, what outcome is confirmed, and what remains unknown.
The existing logging points then grade the information that makes those answers possible. Useful internal diagnostics may include implementation details and sanitized tracebacks; public errors need their own appropriate level of detail.
9.1. Failure logs identify the operation and result  2 points
1 point: Structured log information identifies the operation and whether the provider was involved.
1 point: It identifies the service-level error category and resulting HTTP status, matching the observed response.
Include the existing request or correlation identifier if the service has one. Adding a tracing system or a new identifier mechanism is unnecessary.
An entry containing only “something went wrong” does not establish either condition.
Scoring: Divide each point equally among independently implemented failure-logging paths. Inspect one representative case for a shared implementation and confirm that applicable operations reach it.
9.2. Failure logs distinguish observations from assumptions 2 points
Compare the log claims with what the controlled failure actually establishes.
1 point: Claims about the failed attempt and its cause agree with the available evidence. An attempted action is not reported as a confirmed result.
1 point: When a write’s outcome is uncertain, the logs preserve that uncertainty. They do not claim that nothing changed merely because confirmation was not received.
For example, a timeout after sending a request can leave the write outcome unknown. A locally rejected request that never reaches the provider can establish that no provider write was attempted.
Scoring: Divide each point among applicable failure-handling implementations. If no required operation writes, verify that fact and award the write-outcome point.
9.3. Logs preserve useful context without exposing sensitive data  2 points
1 point: Failure logs contain no credentials, tokens, authorization headers, or sensitive provider data. Inspect the actual output, including exception messages.
1 point: Expected failures produce concise diagnostic information rather than full payload dumps or pages of unhelpful stack traces.
Necessary non-secret resource identifiers are acceptable. Unexpected failures may include a useful traceback when it does not expose sensitive data.
Scoring: Divide each point equally among the applicable logging implementations examined in Section 9.1.

10. Explaining changes 4 points
Inspect a required-operation change and a provider-boundary or injection change. They may belong to the same PR. Use the final descriptions and corresponding integrated commit history.
A future maintainer should be able to recover what changed, why the change was needed, and how it was checked. Put the explanation in the commit or associated PR where it can be found. The same explanation does not need to be repeated in both.
10.1. Commit history identifies substantive changes 1 point
Read the commits that introduced the sampled changes. Their messages should identify the behavior or implementation changed.
“Normalize provider permission failures” identifies a change. “Updates” does not. A commit may rely on its associated PR for the fuller explanation.
Scoring: Divide 1 point equally among the sampled changes. Assess the history retained after the team’s merge process; no minimum commit count or particular message format is required.
10.2. PRs explain the problem, approach, and verification 3 points
For each sampled change, verify:
1 point: The description states the problem and resulting behavior. For a modification, it makes the relevant before-and-after behavior clear.
1 point: It explains the reason for the approach and the assumptions or compatibility consequences that matter to the change.
1 point: It identifies the tests or manual checks used, their observed results, and relevant remaining gaps.
Identify a guarantee or assumption you examined and the evidence supporting your conclusion. If you raise a concern, explain the requirement, counterexample, or consequence that makes it matter. If the implementation is sound, explain what you checked and why it is sound.
Links to existing issues, tests, or verification output may supply details. The explanation must match the final change being reviewed.
Scoring: Divide each point equally among the sampled changes. An honest report of a failing check can earn explanation credit; the unresolved behavior and failing CI are assessed in their respective sections.

11. Team and sister-team reviews 10 points
Use the internal changes examined in Section 10, the sister-team review, and the feedback your team received.
11.1. Sister team examines implementation and verification  3 points
For the sampled internal changes, verify:
1 point: The review identifies a concrete contract, implementation decision, side effect, or boundary that was examined, with a finding or reasoned confirmation.
2 point: The review examines relevant verification: what a test asserts, whether it covers the changed behavior, an observed execution result, or a specific gap requiring attention.
Include review of real-provider wiring and controlled substitution in the provider-boundary sample.
An approval with no supporting review evidence establishes participation but does not establish the other two points. A useful review can explain why the implementation and tests are sound.
Scoring: Divide each point equally among the sampled changes. Review evidence may appear in existing PR threads or a recorded joint review. Human review applies to agent-generated changes as well.
11.2. Sister-team review records actual checks and useful findings  3 points
1 point: Follow the sister team’s setup instructions and attempt its fast tests. Record the steps checked and observed results.
1 point: Attempt the main workflow using its documentation and trace the relevant code, state changes, and provider calls. Consult the associated tests where needed.
1 point: Publish specific findings with relevant evidence and clear intent: blocking issue, design concern, question, optional suggestion, or useful confirmation.
A blocking issue must identify a violated requirement or concrete defect, with a reproduction or counterexample where applicable. Positive findings should explain which design or test was effective and why.
Scoring: Award each point for the demonstrated review activity. If the other team’s setup or workflow is blocked, an exact failing step, observed error, and continued examination of the available code can establish the corresponding review credit. Your score does not depend on the other team’s software succeeding.
11.3. Feedback receives a response and produces a verified improvement 4 points
Inspect substantive feedback from teammate and sister-team reviews.
1 point: Each substantive concern or question has a visible disposition: a fix, an answer, or a reasoned decision to retain the approach.
1 point: The disposition is supported by relevant evidence, such as changed code, a test result, provider documentation, or an explanation of the applicable contract.
1 point: One usability improvement to behavior or documentation addresses an actual difficulty identified through review. The relevant PR explains the difficulty and resulting change.
1 point: The affected behavior or instructions are rechecked, with the expected and observed result recorded.
A resolved-thread marker alone does not establish a response. A follow-up issue may record optional work, but it does not complete missing required behavior.
Scoring: Divide each of the first two points equally among substantive feedback items, treating repeated reports of the same concern as one item. Completed reviews with no substantive concerns receive those points. Award the last two points separately for the justified improvement and its verification. No bug, disagreement, or redesign needs to be manufactured.




12. Engineering decisions and tradeoffs 4 points
Use the decision and operation-cost explanations already required by the assignment.
12.1. Document where you intentionally took on technical debt 3 points
Choose a decision present in the submitted implementation.
1 point: Explain the problem, relevant constraints, and a plausible alternative that could address the problem.
1 point: Give evidence supporting the selected approach and connect it to the implementation. Distinguish observations from assumptions.
1 point: Explain the consequences, remaining uncertainty, and a concrete condition that would make the team revisit the decision.
Evidence may be a provider capability, a test, an experiment, a measurement, or an explicit workload assumption.
For example, using provider identifiers directly may avoid maintaining a mapping store while making a future provider change more costly. The explanation should establish why that tradeoff fits this service.
Scoring: Award each point independently. A sound initial decision earns full credit; introducing technical debt or performing a redesign is unnecessary. Existing documentation or a PR may contain the explanation.
1 point: Explain the selected approach’s known limitations or fragile assumptions, their consequences, and a concrete condition that would make the team revisit the decision.
12.2. One operation has an accurate cost explanation 1 point
Choose an existing operation whose work grows with input size or the amount of data processed. Identify:
The size being considered and relevant data structures.
Time and Space Complexity.
The number of provider calls and the assumptions determining it.
Work delegated to the provider and what remains unknown.
For listing, distinguish records returned from records fetched or inspected. For file or text processing, distinguish the payload size from the number of requests.
Scoring: Award 1 point when the explanation agrees with the implementation and states its assumptions. A benchmark is unnecessary. Request latency alone does not establish local complexity or the provider’s internal algorithm.

Extra Credit +10 pts each
[ +10 pts ] Caching: Define cache keys, expiration, invalidation, bounded storage, and permitted staleness. Demonstrate a cache hit and expiry/invalidation and show the provider-call difference.
[ +10 pts ] Idempotency keys: Define key scope, retention, payload conflicts, restart behavior, and uncertain outcomes. Demonstrate that repeated/overlapping requests do not duplicate the promised logical action.
[ +10 pts ] Conditional updates: Demonstrate two clients reading the same version and show that a stale overwrite is prevented or rejected.
[ +10 pts ] Streaming: Transfer representative data with bounded memory; measure memory and demonstrate cleanup after interruption.
[ +10 pts ] Background work: Accept work, expose status, interrupt the system, and demonstrate the documented recovery and duplicate-execution behavior.
[ +10 pts ] Overload protection: Apply controlled load and demonstrate bounded resources and predictable behavior using a justified limit.
[ +10 pts ] Release and recovery: Deploy a release, introduce a controlled release failure, recover using the documented procedure, and have a teammate independently follow it.
