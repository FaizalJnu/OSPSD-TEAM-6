Level 5: Handle Failures Consistently
Your service now has a clear provider boundary and a replaceable implementation. Next, define what happens when an operation does not succeed.
5.1. Your goal
Define a small, consistent error model for your service and use it to handle at least one expected failure end to end.
A caller should be able to distinguish different classes of failure without reading your source code or depending on provider-specific error messages.
5.2. What should happen?
Suppose a caller requests a resource that does not exist.
The provider may represent that failure in its own way:
Provider SDK exception
        ↓
provider-specific error
        ↓
your provider implementation
Your service should translate that failure before it reaches the caller:
provider-specific failure
        ↓
provider-independent error
        ↓
HTTP response
For example:
GET /<resource-type>/missing-id
might return:

{
  "error": {
    "code": "not_found",
    "message": "Resource not found"
  }
}
with an appropriate HTTP status code.
This is only an example. Your team should define an error format appropriate for your service.
5.3. Specification
Define a consistent structure for application errors.
At minimum, your service should distinguish:
invalid input;
a resource that does not exist;
an applicable access or permission denial;
a provider failure that prevents the operation from completing.
Your public API should not expose raw provider exceptions or provider-specific error objects directly.
For each error your service exposes, document:
when it occurs;
the HTTP status code;
the application error code or type;
the response shape;
whether the caller can reasonably retry the request.
Do not report a failed operation as a successful one.
5.4. What you need to think about
Before implementing, agree as a team on:
Which failures belong to the caller?
Which failures come from the provider?
Which provider failures should map to the same service-level error?
What information is useful to the caller?
What information should remain internal?
Which failures should be logged?
Which failures are expected and which indicate a bug?
Should a caller be able to retry the operation?
Avoid copying provider error messages directly into your public contract.
Your error model should describe your service, not the provider.
5.5. Logging
Add lightweight structured logging for failed operations.
At minimum, a useful failure log should make it possible to identify:
the operation;
the error category;
whether the provider was involved;
the resulting HTTP status;
a request or correlation identifier if your service has one.
For example:
{
  "level": "WARN",
  "operation": "get_resource",
  "error": "not_found",
  "status": 404
}
Do not log secrets or sensitive provider data.
Avoid logging:
API keys;
OAuth tokens;
authorization headers;
credentials;
unnecessary request or response bodies.
Expected failures should not produce pages of unhelpful stack traces.
5.6. Design and testing
Use the controlled provider implementation from Level 4 to reproduce failure cases deterministically.
At minimum, add tests for:
one successful request;
one invalid request;
one missing resource;
one provider failure.
The tests should verify the public response, not the provider exception that caused it.
For example, your controlled provider might be configured to return:
resource missing
and your application test should verify that the caller receives the error contract your service defines.
Also verify at least one real provider failure manually or through an integration test where practical.
5.7. Team integration
Error behavior is part of your public API and should be reviewed by the team.
Before merging, agree on:
the error response shape;
error naming;
HTTP status mappings;
which failures are safe to expose;
which failures should be logged;
which failures may be retried.
A caller should see the same style of error regardless of which team member implemented the operation.
5.8. You don't need these yet
You are not required to:
implement automatic retries;
implement exponential backoff;
build a circuit breaker;
handle every provider-specific error;
create a complex exception hierarchy;
add centralized observability infrastructure;
support rate-limit recovery;
implement idempotency.
Focus on a small, consistent error contract and a few important failure cases.
5.9. When you're done
This level is complete when:
your service exposes a documented and consistent error format;
expected provider failures are translated before reaching the caller;
callers can distinguish invalid input, missing resources, access denial, and provider failure;
failure cases are covered by tests using your controlled provider implementation;
expected failures produce useful, sanitized logs;
your team can explain which failures belong to the public contract and which remain internal.
Congratulations on making it so far!
